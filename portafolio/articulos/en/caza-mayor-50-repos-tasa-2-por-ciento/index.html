I swept 50 repositories: two real defects and a 2 % hit rate

I measured 765 workflow files in 50 repos with more than 5 000 stars: 262 steps invoke a test runner and 11 cannot make the workflow fail. The defensible-defect rate is 2 %, and the most severe one sits in the deadest repository.

0 · Verdict in one line

Of 50 company repositories with CI (≥ 5 000 ★, AI/DevTools/Fintech), 1 today has a CI-signal defect that I would sign with my name in their repo; the other two targets have a real defect but a different condition, and here I say which is which instead of selling all three the same.

1.1 · Self-audit of the instrument (three corrections measured in this turn)

  1. The first classifier was blind to needs: gates. v1 only looked at later steps within the same job. v2 added needs: consumers and needs.X.result guards → same result (10 vs 10). The number survived, but the argument was not proven until it was tested.
  2. The runner regex was short. It did not see make test, dotnet test, bazel test, phpunit, rspec. Extended: 262 steps, +1 repo (Arize-ai/phoenix, bot workflow). The rate moved from 4/50 to 5/50 and the defensible-target rate did not move.
  3. The crawl's «CI pain» ranking was contaminated and is discarded. It counted runs from fork branches and action_required (a workflow that never actually executed) as failures. Measured in openai/evals: 11 of 15 recent runs are action_required — hence the 0.99 of the first pass. A repo with healthy CI can produce that figure. The ranking is withdrawn; it is used in no decision in this document.

3 · Target 1 — livekit/agents (the only one I sign)

The defect, verbatim in test-stt.yml@055744e1505b:201

- name: Run STT tests
  run: |
    uv run pytest -n 3 -v --stt --tb=long --junitxml=test-results.xml 2>&1 | tee test-output.txt || true

Two independent layers erase the result:

  1. || true turns any non-zero exit into 0.
  2. Even if || true is removed, the pipeline ends in tee, and in the default bash (no pipefail) the step status is tee's, which is 0 as long as it can write the file. Deleting || true outright does not restore the gate — this is what separates a superficial reading from a measurement.

Why it is probably not what you meant

The later steps are already written to run no matter what (Generate test summary and Post results to PR carry if: always()), and pytest --junitxml writes the XML on failure too. The || true is not needed for the report to exist: always() already bought that. The only thing it buys is that a red STT suite is indistinguishable from a green one in the checks list.

The contrast that makes the report credible

The same repository already implements the correct pattern in ci.yml:34-43: continue-on-error: true on ruff plus a Report ruff errors step with if: steps.ruff-check.outcome == 'failure' || … that does exit 1. That is: the house knows how to close a gate. test-stt.yml is an inconsistency, not a philosophy.

8 · The corrected strategy

«The Sniper» (find the hidden defect in 50 repos and shoot) measured 2 % live targets. Its real cost is not the scan: it is that 49 out of every 50 attempts produce nothing and the shot is spent on a dead repo or on a defect the owner declared on purpose.

«The Interlocutor» inverts the load: you do not look for the defect, you enter where the pain is already written and bring the measurement the author does not have. The client declares the pain; the instrument is the only thing contributed. It applies to the same channel, with the same public signature and a much lower cost per attempt.

One entry rule: no comment without a measurement the issue author does not already have. If the comment can be written without running anything, it is not written.
