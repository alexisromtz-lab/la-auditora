1. What was left open, said with the figure next to it

The previous addendum closed the rate of RC 2 and RC 4: 33 cases, 100 % formal, 15.2 % substantive. And it declared its own residue on the same page: RC 1 (60) and RC 5 (308) still had no rate.

That means 368 of the 612 published observations — 60.1 % of the numerator — had no verdict. A client asking "what is your false-positive rate?" received an answer that held for 33 cases and was presented as if it held for 612. That was the weakness, and it was not hidden: it was written down.

It is no longer open.

2. The measurement

Same discipline as last time, and in the same order: first the prediction, then the reading.

A pre-registration was written (preregistro_tpr_rc1_rc5_20261030.json, 129 lines, blob 05eaead8) with the substantive classes, the declared bias and five falsifiers, before opening a single run: or a single uses:. Then the 163 workflow files of the batch were re-downloaded by blob SHA from the GitHub API and their sha256 verified against the manifest: 163/163 identical, 0 failures. The engine reproduced the exact split: RC 1 60 · RC 2 30 · RC 4 3 · RC 5 308.

class reading result
RC 5 REF_MUTABLEdoes the cited uses: exist in the raw text and is its ref really floating?308/308, 0 false positives

The two negative controls are the part that matters. An engine that flagged everything would have given 1321 instead of 308, and 174 instead of 60. It does not: it discriminates in both directions of the conjunction.

3. The substantive rate: this is where the number shrinks

Formal 100 % is not the figure that can be sold, and the previous addendum already said so for RC 2. For RC 1 and RC 5 the effect is larger, because these two classes are measured per occurrence and not per risk.

RC 5 — 308 occurrences are not 308 risks: they are 31

The RC 5 sweep does not deduplicate. The same action repeated across twenty jobs yields twenty findings. In the 163 files there are 1321 uses: values, of which 308 are floating… and those 308 are only 31 distinct references. Publishing 308 without saying so would be inflating the numerator through the back door.

The other 256 are split into 239 actions/*, which for a client is noise (control of the ref belongs to GitHub, not to the attacker the client fears), and 17 placeholders that do not resolve and are counted as their own class in §4, not as third party.

4. The two classes the prediction did not have

On two consecutive days, the same pattern: the taxonomy falls short and the new class shows up in the same place where the engine reads well. Yesterday it was NO_SUMIDERO (16 of 33). Today there are two, and both are declared instead of being forced into place.

R7 — unsubstituted placeholder: 17 occurrences, 3 literals, 3 repositories and 6 files. The raw bytes contain local references written with GitHub's template placeholder ($/…) that was never substituted: $/.github/actions/setup 5 times, all in sveltejs/svelte ci.yml; $/.github/actions/issues-helper 11 times in vitejs/vite —6 in bot.yml, 3 in issue-labeled.yml, 1 in issue-close-require.yml, 1 in lock-closed-issues.yml—; and $/.github/workflows/notify-resolved-issues.yml 1 time in nuxt/nuxt release.yml. The bytes are genuine from the origin: the git hash-object of the six files matches one by one the blob_sha declared by the manifest, so it is not an artefact of the download. Its severity stays NOT_MEASURED, for the same reason as NO_SUMIDERO: 0 if one reads that a uses that does not resolve holds no custody, and "the strongest finding" if one reads that the file declares an intention it does not execute and whoever audits it will believe it is pinned. Resolving it requires knowing whether the repo generates that file or commits it as is, and the file does not say.

Correction with a chain (HUELLA-ADDENDUM-R2-R7-POR-ARCHIVO-20261030). The previous version of this paragraph, written hours earlier and never published, named facebook/react as one of the repositories with placeholders. Measured over the 163 workflows already verified by sha256: facebook/react has 26 workflows and zero occurrences, and the 17 are in svelte (5), vite (11) and nuxt (1). The count never changed — 17 occurrences, 3 literals — the attribution did. It is the third case of the same defect in the day: a structured field that is correct next to a sentence that is not derived from it, just like the 22.4 % in §5. The correction travels with the census, field clase_no_prevista.correccion_con_cadena.

A7 — the lexeme matches while nothing is executed: 6 of 60. An echo " - NPM name: …" matches the npm pattern. A yq '.allowBuilds[]=false' -i pnpm-workspace.yaml matches because the name of the file says pnpm. It is not a defect of the engine — its declared domain is lexical per line — but it is noise for a client, and that is why it is counted separately and published: it is how a false positive survives the correction of the engine.

5. Four defects of the reader, found before publishing

The lesson from last time was applied with a will: the reader is wrong too, and when it is wrong it declares the correct instrument guilty. An independent desk reader, without the engine's parser, found four:

  1. permissions: {} read as {'{}': 'write'} → RC 1 inflated from 60 to 121 (61 false reds).
  2. The job uses: counted twice → RC 5 inflated from 308 to 319 (11 false reds).
  3. Quoted permission values (contents: 'read') keeping the quotes → a real job fell out: 59 of 60.
  4. run: folded over several lines read only on the first → a cited line appeared truncated.

All four were the reader's. The engine did not change a single line: its formal output holds 368/368.

7. What still has no rate, and why it is said

SC1 — 211 observations, and they are not all the same thing. They are not from the gate: they are the substitution and chain count of the harness itself. This act measures 368 of 612 observations (60.1 %) — but that denominator is not the one for findings, and confusing them is the defect this addendum already committed once with another figure. Of the 244 without a census, 156 are REVIEW by contract design (SC1_JOB_WRITE_SCOPE_REVIEW 153 + SC1_ROOT_READ_ALL_REVIEW 3): they are inventory, not findings, and there is no rate to assign them because they do not assert a vulnerability. 55 are a real conjunction (SC1_ROOT_PERMISSIONS_MISSING 36 + SC1_ROOT_WRITE_INHERITED 19). And 33 are the corrected class (RC 2 30 + RC 4 3), validated by domain review with a chain, not by census. Over the denominator a CTO would want — the one for those that assert a vulnerability, 456 — the coverage is 368/456 = 80.7 %, and what is left to census is 55 cases, 9.0 % of the total, not 211. What is published as 60.1 % is still correct as long as the denominator is "observations"; it stops being so the moment the denominator is "findings".

8. The sentence that can be published

612 observations, of which 456 assert a vulnerability. Census: 368 — 80.7 % of the findings and 60.1 % of the observations. Of the remaining 244: 156 are REVIEW inventory by contract, 55 are a real conjunction without a census and 33 are the corrected class, validated by domain review. Formal TPR 368/368. Negative control: 1013 pinned refs not flagged and 164 jobs without write not flagged. Substantive: 10 of 60 authority findings exercise or hand over the credential; 11 distinct references of third parties across 308 floating-ref occurrences; 17 references that do not resolve — 5 in sveltejs/svelte ci.yml, 11 in four workflows of vitejs/vite (6 of them in bot.yml), 1 in nuxt/nuxt release.yml — with severity NOT_MEASURED.

There is no round number and there is not going to be one. What there is, is an instrument that was wrong 195 times, published it, corrected itself, measured its own rate, found four defects in its reader and published those too, and left in plain sight what it could not measure. That is what a CTO can audit. A "1000 vulnerabilities" is not.

9. Publishing note: the declared format and the executed format

The previous addendum was written in Markdown and published without it. Measured today against the public API (GET /api/articles/4950016, HTTP 200, published_at 2026-10-31T00:18:48Z): the stored body_markdown contains 0 **, 0 backticks, 0 | and 0 ##. The loss is not in the render: it is in the source. That is why the format is not recovered by switching modes in the editor — the body has to be rewritten.

And there is a detail that is a mechanism, not an accident: of the two HTML comments in the published body, the one that opened a line lost its < (!-- HUELLA-TPR-MEDIDA…, visible as text) and the one that came inline behind the --> survived intact (<!-- HUELLA-NO-SUMIDERO-MEDIDO…). Falsifiable rule with n=1 body: Dev.to removes the first < of a line that starts with <; the following ones on the same line survive. It is not "the start of the body", as was declared in the first reading: the body starts with text, not with <. A single observation is not a rule: it is published with its n and its falsifier.

Operational consequence, applied in this very document: no fingerprint of this revision travels as an HTML comment; they travel as code text, in the header and in the footer. It is the same defect this document measures in the others: a declared intention — the format, the fingerprint, the permissions: — that the execution environment does not execute.
