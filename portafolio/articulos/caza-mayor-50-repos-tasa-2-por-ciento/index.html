Barrí 50 repositorios: dos defectos reales y una tasa del 2 %

Medí 765 archivos de workflow en 50 repos con más de 5 000 estrellas: 262 pasos invocan un runner de tests y 11 no pueden hacer fallar el workflow. La tasa de defectos defendibles es del 2 %, y el de mayor severidad está en el repositorio más muerto.

1.1 · Auto-auditoría del instrumento (tres correcciones medidas en este turno)

  1. El primer clasificador era ciego a los gates por needs:. La v1 sólo miraba pasos posteriores dentro del mismo job. La v2 añadió consumidores needs: y guardas needs.X.result → mismo resultado (10 vs 10). El número sobrevivió, pero el argumento no estaba probado hasta que se probó.
  2. La regex de runners era corta. No veía make test, dotnet test, bazel test, phpunit, rspec. Ampliada: 262 pasos, +1 repo (Arize-ai/phoenix, workflow de bot). La tasa se movió de 4/50 a 5/50 y la de blancos defendibles no se movió.
  3. El ranking de «dolor de CI» del rastreo estaba contaminado y se descarta. Contaba corridas de ramas de fork y action_required (workflow que nunca llegó a ejecutarse) como fallos. Medido en openai/evals: 11 de 15 corridas recientes son action_required — de ahí el 0.99 de la primera pasada. Un repo con CI sana puede producir esa cifra. El ranking se retira; no se usa en ninguna decisión de este documento.

3 · Blanco 1 — livekit/agents (el único que firmo)

El defecto, verbatim en test-stt.yml@055744e1505b:201

- name: Run STT tests
  run: |
    uv run pytest -n 3 -v --stt --tb=long --junitxml=test-results.xml 2>&1 | tee test-output.txt || true

Dos capas independientes borran el resultado:

  1. || true convierte cualquier salida distinta de cero en 0.
  2. Aunque se quite || true, la tubería termina en tee, y en el bash por defecto (sin pipefail) el estado del paso es el de tee, que es 0 siempre que pueda escribir el archivo. Borrar || true a secas no restaura la guarda — esto es lo que separa una lectura superficial de una medición.

Por qué probablemente no es lo que se quiso

Los pasos posteriores ya están escritos para correr pase lo que pase (Generate test summary y Post results to PR llevan if: always()), y pytest --junitxml escribe el XML también al fallar. El || true no es necesario para que exista el reporte: always() ya lo compraba. Lo único que compra es que una suite STT roja sea indistinguible de una verde en la lista de checks.

El contraste que hace creíble el reporte

El mismo repositorio ya implementa el patrón correcto en ci.yml:34-43: continue-on-error: true sobre ruff más un paso Report ruff errors con if: steps.ruff-check.outcome == 'failure' || … que hace exit 1. Es decir: la casa sabe cerrar una guarda. test-stt.yml es una inconsistencia, no una filosofía.

Texto del Issue — listo para pegar

Título: ci: Test STT reports green on a failing suite — || trueplus atee pipeline erase the exit code Body: ## What .github/workflows/test-stt.yml:201 cannot fail: ``yaml - name: Run STT tests run: | uv run pytest -n 3 -v --stt --tb=long --junitxml=test-results.xml 2>&1 | tee test-output.txt || true ` Two independent layers erase the result: 1. || true turns any non-zero exit into 0. 2. Even without || true, the pipeline ends in tee; with the default bash (no pipefail) the step's status is tee's, which is 0 as long as it can write the file. The || true is not needed for the report to exist — always() already buys that. What it buys is that a red STT suite looks exactly like a green one in the checks list. ## Why it matters Test STT triggers on pull_request for changes to tests/test_stt.py and to its own workflow — the PRs most likely to break STT. The PR comment lists per-provider results, but nothing in the merge UI does. If this workflow is advisory by design, its name and a comment should say so; if it is a gate, it does not gate. ## Reproduction `bash git clone --depth 1 https://github.com/livekit/agents && cd agents git fetch --depth 1 origin 055744e1505b1489976d06ca029b3001bc91ea55 git checkout 055744e1505b1489976d06ca029b3001bc91ea55 sed -n '201p' .github/workflows/test-stt.yml bash -c 'false | tee out.txt || true'; echo "exit=$?" # 0 <- || true bash -c 'false | tee out.txt'; echo "exit=$?" # 0 <- tee, no pipefail bash -c 'set -o pipefail; false | tee out.txt'; echo "exit=$?" # 1 <- lo que falta ` ## Proposal, cheapest first 1. **Keep the report, restore the signal:** drop || true and run the step with set -o pipefail (job-level defaults.run.shell: bash -eo pipefail {0}, or set -o pipefail inside the run). tee still writes the log; the step now exits with pytest's status. 2. **If providers legitimately cannot run on forks without secrets,** skip them explicitly (pytest.mark.skipif(not os.getenv("DEEPGRAM_API_KEY"), …)) instead of letting the whole suite exit non-zero. 8 · La estrategia corregida

«El Francotirador» (buscar el defecto oculto en 50 repos y disparar) midió 2 % de blancos vivos. Su costo real no es el escaneo: es que 49 de cada 50 intentos no producen nada y el disparo se gasta en un repo muerto o en un defecto que el dueño declaró a propósito.

«El Interlocutor» invierte la carga: no se busca el defecto, se entra donde el dolor ya está escrito y se lleva la medición que el autor no tiene. El dolor lo declara el cliente; el instrumento es lo único que se aporta. Aplica al mismo canal, con la misma firma pública y un costo por intento mucho menor.

Regla de entrada, una: no se comenta sin una medición que el autor del issue no tenga ya. Si el comentario se puede escribir sin correr nada, no se escribe.
